# Pico W JPEG連番プレーヤー（6 fps 映像テスト）

既存のJPEG連番をRaspberry Pi 5からTCPでPico Wへ送る映像テストです。RAW/JPEG比較版を同一Pico Wで実機試験済みです。元画像は読み取りのみです。音声は含みません。後から追加したYouTube URL指定Webと専用userサービスは末尾の「Web URLプレーヤー」に記録しています。

## 確認した入力

`/home/tane/Videos/voltesV_6frame` に `frame0001.jpg`〜`frame0588.jpg` の588枚があり、欠番・余分なファイルはなく、すべて160×80 JPEGでした。6 fpsでは98秒分です。作成時のffmpegコマンドはユーザー申告のものをそのまま記録します。

```sh
ffmpeg -i $1 -vf "crop=440:242:(in_w-440)/2:(in_h-220)/2,scale=160:80,fps=6" -q:v 5 frame%04d.jpg
```

## 構成と通信

- `server/streamer.py`: Pillowで全フレームを読み込み、RGB565または品質90 JPEGで送信します。RAWでは約15.1 MBをメモリに保持します。TCP切断後は再接続を待ち、動画の経過位置から配信を続けます。
- `diagnostics/server/lcd_pattern.py`: 同じ通信方式で黒地・白1px外枠・赤緑青の細線と太線を固定表示し、液晶の位置と色を確認します。
- `pico/pico_player.c`: Wi-Fi接続後、PWF2ヘッダー20バイトとRAW/JPEG画像を完全受信し、選択モードに応じてJPEG展開とSPI表示を行います。切断や不正ヘッダー時に接続し直します。受信済みフレームを保護する2画面バッファです。遅延比較後、Wi-Fi省電力を無効にしています。
- `pico/config.example.h`: Wi-Fiと液晶調整の設定例。実値はローカルの `config.h` に記入します（Git除外）。
- [現在の配線図と対応表](docs/wiring.md)、[完成形の概念配置と別配線案](docs/compact-layout.md)。BLKは現在未接続で、基板仕様は未確認です。

新ファームの1フレームは `PWF2` の20バイトヘッダー（magic、連番、幅、高さ、データ長、モード）とRAW 25,600バイトまたは可変長JPEGです。RAWでは計25,620バイト、6fpsで153,720バイト/秒（約1.23 Mbit/秒、TCP等のオーバーヘッドを除く）です。サーバーは単調時計で6 fpsを管理し、遅れたフレームを飛ばします。クライアントは2画面分のバッファでTCPの分割受信に対応します。Picoは同じTCP接続の逆方向にSTA MAC、受信・展開・描画・破棄フレーム数、JPEG展開とSPIの所要時間を毎秒PWS3の80バイトで返します。音声と同期信号はありません。

## 必要なもの

- Raspi5: Python 3、Pillow (`python3-pil` または `python3 -m pip install -r server/requirements.txt`)
- Pico Wビルド: Pico SDK、CMake、ARM GCC。Raspi5では `/home/tane/dev/PicoW/pico-sdk` と `/usr/bin/arm-none-eabi-gcc` を確認済みです。
- 実機: Pico W、80×160 SPI液晶。裏面基板印字は `DRIVER IC: ST7735S` と確認済みです。固定画面で、ユーザーが `LCD_Y_OFFSET=24` の四辺の白枠と赤・緑・青の発色を確認しました。

C SDKを選んだ理由は、SPIとWi-Fiを並行して扱うためのSDKとクロスコンパイラが既にあり、25,600バイトの連続SPI転送と切断復帰を固定メモリで実装できるためです。ソース自体は6 fpsで、動画由来のコマ送り感とネットワーク遅延による停止は区別して評価します。

## サーバーの実行

ポートは設定可能で、初期候補は **16151** です。既存本番の16150は使用しません。Picoから接続する場合はRaspi5のLANアドレスで待ち受けます。例:

```sh
cd /home/tane/dev/PicoW/PicoW_Youtube_Player
python3 -m server --host 0.0.0.0 --port 16151 --frames /home/tane/Videos/voltesV_6frame --compensate-colors
```

Ctrl+Cで停止します。`--once` は1周送信後に終了し、省略時はエンドレスです。`--compensate-colors` は診断画面で確認された反転と赤/青入れ替えをPi5側のJPEG→RGB565変換後に補正します。Pico側の `LCD_INVERT=1`、`LCD_MADCTL=0x60` はそのままです。送信が詰まった場合は既定の2秒（`--send-timeout` で変更可）でそのTCP接続を切り、Picoの再接続後に動画時刻から続けます。デフォルトはローカルホスト待受で、LAN公開は明示指定した場合だけです。起動前にポートの空きと接続先LANアドレスを再確認してください。サーバーは一度に1台へ配信します。

Pico接続中はサーバーに `received`, `displayed`, `dropped`, `display_rate`, `SPI` と配信側の5秒ごとの送信速度・スキップ数・動画内フレーム番号が出ます。最初の起動時に3秒間、白枠と赤・緑・青の帯を表示します。固定診断ではユーザーが色と四辺の枠を確認しました。動画が6 fpsのため、通信が正常でも毎秒6コマ固有の動きになります。

## Pico側の設定とビルド

1. 既存のローカル `config.h` を保持し、必要な場合だけWi-Fi設定、`SERVER_IP`、ポートを本人がローカル編集します。`pico/config.example.h` は新規環境向けの見本です。秘密値を表示・コミットしないでください。**転送前に `--clean-first` で再ビルド**してください。
2. BLK内部回路は未確認です。BLK未接続の現在の配線で映像表示は確認済みです。表示位置・向き・色順は `config.h` の `LCD_X_OFFSET`, `LCD_Y_OFFSET`, `LCD_MADCTL` を調整します。BGR切替は `LCD_MADCTL` の `0x08` ビット、反転は `LCD_INVERT`。現在のブレッドボード配線は `DISPLAY_PROFILE=0`、完成形の別配線案は `DISPLAY_PROFILE=1`。本テストはBLK制御ピンを使いません。
   現在の設定は `LCD_INVERT=1`、`LCD_Y_OFFSET=24` です。26から25へ変えても上端のノイズ行と下端の白枠欠けが残ったため、もう1行上げました。固定画面で色はPi5側の `--compensate-colors` を使って確認しました。
3. ビルド手順:

```sh
cd /home/tane/dev/PicoW/PicoW_Youtube_Player
PICO_SDK_PATH=/home/tane/pico/pico-sdk cmake -S . -B build -DPICO_BOARD=pico_w \
  -DCMAKE_BUILD_TYPE=Release -DPLAYER_LCD_GAMMA_LGFX=ON
cmake --build build --clean-first -j2
```

Pico側IPv4は既定で `192.168.0.173/24`、ゲートウェイとDNSは `192.168.0.1` に固定します。これらはPi5の現行LAN設定から確認した値で、`CMakeLists.txt` の `PLAYER_STATIC_IP`, `PLAYER_GATEWAY`, `PLAYER_NETMASK`, `PLAYER_DNS` をCMakeオプションで変更できます。ルーター側のDHCP予約や他機器の設定は変更しません。Pi5側が代理ARPを返すため、Pi5からのpingだけでは `.173` に他機器がいないことを証明できません。ルーターの割当範囲・予約状況は別途確認してください。

完成形候補のGP9〜13/SPI1配線を使う場合は、同じSDKで別buildディレクトリを指定し、`-DDISPLAY_PROFILE=1 -DPLAYER_LCD_GAMMA_LGFX=ON` を付けて再ビルド・転送が必要です。既存GP17〜21/SPI0配線の既定値は0です。[背中合わせ概念案](docs/compact-layout.md)と[現配線](docs/wiring.md)を参照してください。寸法・端子位置・BLK回路は現物確認が必要です。

生成物は `build/pico_w_jpeg_player.uf2` です。PWF2比較版は同一Pico Wへ書込み済みで、Flash Verify 100% OKを確認しました。BLKを勝手にGPIOへ接続しないでください。

## 固定画面の診断

動画配信を止めてから、同じ16151番で次を起動します。Picoへの再書込みは不要です。

```sh
python3 -m diagnostics.server.lcd_pattern --host 0.0.0.0 --port 16151
```

黒背景、四辺の白1px枠、上端内側の赤・緑・青各1px線と、少し下に同順の8px帯を出し続けます。上端にノイズ行がある場合は太線の色で判断します。Ctrl+Cで終了します。色と位置を確認してから動画配信へ戻してください。

実画面で「黒→白、赤→黄、緑→紫、青→水色」が観察されたため、Picoのファームを変えずに反転と赤/青の入れ替えを打ち消すオプションを設けました。ユーザーはこれを使った固定画面で、黒背景・白枠・赤緑青の色を確認しました。動画配信も同じ `--compensate-colors` を使います。

```sh
python3 -m diagnostics.server.lcd_pattern --host 0.0.0.0 --port 16151 --compensate-colors
```

## テスト

```sh
python3 -m unittest discover -s tests -v
python3 - <<'PY'
from pathlib import Path
from server import streamer as server
frames = server.load_frames(Path('/home/tane/Videos/voltesV_6frame'))
print(len(frames), len(frames[0]), len(server.packet(0, frames[0])))
PY
```

新PWF2版の期待値は `588 25600 25620` です。ソフト単体試験は液晶の発色、向き、BLK点灯、実機での安定6 fpsを証明しません。

実機のエンドレス試験では動画時刻が1周98秒を超えて先頭側へ戻ることを確認しました。TCPの再送・送信待ちとPico側のフレーム破棄があり、最初の約98秒でPicoの描画カウンタは約382枚（約3.9 fps）増加しました。SPI転送は通常約15.6ms/画面で、167msの6fps枠より短いです。ソース時刻は6fpsで進み、遅れたフレームを飛ばすため、588枚すべてが画面に到達したという意味ではありません。安定した6fps描画は今後の通信経路改善事項です。

動きの内訳を調べる場合は通常の動画コマンドに `--trace-motion` を加えます。現行TCPのまま、サーバーの送信間隔・`sendall` の待ち時間と、Picoが毎秒返す受信/描画/破棄数を記録します。最初の101秒の実機計測ではPico描画418枚（約4.14fps）、両スロット満杯による破棄95枚、描画0枚の1秒区間18回（連続最長約7秒）、Pi5の送信待ち最大約6.9秒を観測しました。元動画の6fpsによる一定のコマ送りに加え、通信停滞と到着後の連続描画が不規則なカクつきの原因です。

Pi5のTCP状態を停止と同時に確認すると、受信窓はゼロではなく、未ACKセグメントの再送で輻輳ウィンドウが1になり、RTOが指数的に伸びていました。省電力を無効にしても停止は残ったため、サーバー側に2秒の送信期限とTCPリセットによる再接続を加えました。同じ省電力無効ファーム・同じ動画で、従来の10秒期限は122.6秒中に描画564枚（4.60fps）、送信待ち最大3.10秒、受信した約1秒間隔の状態報告で描画0枚の区間13回（連続最長3回）でした。2秒期限では110.1秒中に描画549枚（4.98fps）、送信待ち最大2.00秒、描画0枚の区間7回（連続最長1回）でした。ユーザーも長い停止の減少を確認しました。さらに241秒まで観察した結果、送信待ちは最大2秒に収まり、平均描画4.88fpsでしたが、状態報告自体が最大約5秒途切れました。この累計カウンタだけでは画面停止の厳密な最長時間は分かりません。無線状態の短期変動があるため、常に同じ改善幅になる保証はありません。安定した6fps描画は未達です。

再接続までの空白は、動画連番で追うと約3〜10秒の例があります。2秒という値はサーバーの1回の送信待ちの上限で、画面停止の上限ではありません。負荷を切り分けるため、一時的に `--fps 1` で同じRGB565フレームを75.6秒送ったところ、表示バッファ満杯による破棄は0枚でしたが、送信2秒タイムアウトは3回、再接続は4回起きました。したがって画面バッファ不足やSPI表示頻度だけでは通信損失を説明できません。無線経路とPico側のWi-Fi/lwIP受信処理を分けるには、Pico側の受信ドロップ統計や電波強度など追加の診断が必要です。比較後は6fps配信へ戻しています。

診断版ファームウェアでは、従来の32バイト `PWS1` に代えて60バイトの `PWS2` 状態を毎秒返します。Pi側 `server/streamer.py` は両形式を読めます。追加項目は10秒ごとのSTA RSSI（取得前・取得失敗時は `-127`）、lwIPのPBUF_POOL最大使用数と割当失敗数、TCP drop/memerr、Picoの受信コールバック最長実行時間と受信コールバック間の最長空白です。PBUF_POOLの現在容量は32です。統計は起動後の累計または最大値で、lwIPの一部カウンタは16ビットで折り返します。受信コールバックの時間はWi-Fiドライバ内部の処理時間を含みません。RSSI取得は受信コールバック外のメインループで行います。

この診断版を同じPico W（Flash ID `0xE661640843239D21`）へ転送し、Flash Verify 100%を確認しました。SDKは `9a4113fbbae65ee82d8cd6537963bc3d3b14bcca`、内包cyw43-driverは `c1075d4bc440422cf2b2fd12c64a1f53f77660ee` です。同じ588枚・6fps・2秒送信期限で約120秒観測した時、PWS2状態69件でRSSIは−45〜−30dBm、PBUF_POOL最大使用18/32、割当失敗0、lwIP TCP drop/memerrとも0、受信コールバック最長1,298µsでした。一方で送信タイムアウトは11回、再接続は11回起きました。Picoのpbuf枯渇やアプリ受信コールバックの長時間処理を示す値は出ていません。lwIPより前のCYW43処理、アクセスポイント、無線経路のどこで損失が起きるかは、この統計だけでは分かりません。診断版のRSSI取得が通信に与える影響も未測定です。

RSSI取得の影響を比較するため、現在のソースは `SAMPLE_RSSI=0` とし、10秒ごとの `cyw43_wifi_get_rssi()` 呼出しだけをコンパイルから外しています。PWS2の60バイト構造と残りのカウンタは同じで、RSSI欄は常に未取得値 `-127` です。RSSI有効版は `/tmp/picow_pws2_rssi_on.uf2`、無効版は `/tmp/picow_pws2_rssi_off.uf2` に保全しました。無効版も同じFlash IDのPicoへ転送し、Flash Verify 100%・PWS2の `RSSI=-127` を確認しました。この比較時にPicoで動作していたのはRSSI無効版です。RSSI呼出しは有効版ではメインループ内で行い、CYW43ドライバのioctl応答待ち上限はこのSDK設定で1秒です。実際の1回ごとの所要時間は計測しておらず、PWS2状態送信・統計読取り自体の影響もゼロとは断定できません。

同じ588枚・6fps・2秒送信期限の最初の約120秒を動画連番0〜720で比べると、RSSI有効版は送信タイムアウト10回・接続11回・表示カウンタ+253枚（約2.11fps）・破棄+27枚、無効版はタイムアウト10回・接続11回・表示+249枚（約2.08fps）・破棄+43枚でした。完了した送信の最大間隔は有効版1,962ms、無効版2,024ms。タイムアウト後の動画連番の最大空白はそれぞれ約9.3秒、約10.2秒です。これは画面の厳密な最長フレーム間隔ではありません。両版ともPBUF_POOL最大使用18/32、割当失敗・lwIP TCP drop/memerrは0。受信コールバック最長は有効版1,298µs、無効版1,395µs。取得を止めても長い送信停止は残り、今回の条件ではRSSI取得が主因とは言えません。無線状態が時間で変わるため、少数の順次比較だけで小さい影響の有無まで断定できません。無効版の別途75秒間のTCP読取では再送バイト最大216,720B、RTO最大3,488ms、輻輳ウィンドウ1のサンプル72/268でした。有効版には同じ期間のTCPサンプルがないため、再送量の数値比較はできません。

TCP切断のたびにWi-Fi参加を再実行していたため、次の比較用ファームではSDKの `CYW43_LINK_UP`（Wi-FiリンクとIPアドレスが有効）ならTCP接続だけを開き直すようにしました。リンクが落ちていれば従来どおりWi-Fi参加を試みます。無受信判定5秒、TCP監視周期5秒、1秒の再接続待ち、LCD、PWS2、RSSI無効は変更していません。旧RSSI無効版UF2は `/tmp/picow_pws2_rssi_off.uf2`、当時のTCPのみ再接続版は `/tmp/picow_pws2_tcp_only_reconnect.uf2` に保全しました。新しいTCPのみ再接続版は同じFlash ID `0xE661640843239D21` のPicoへ転送し、Flash Verify 100%と起動を確認しました。12件のソフトテストも成功しました。TCP送信の最初のパケット損失を解決する変更ではなく、再接続時の動画空白を比べるための変更です。

同じ588枚・6fps・2秒送信期限の動画連番0〜720（約120秒）では、新版は送信タイムアウト2回、接続3回、PWS2表示カウンタの増分は約559枚（約4.7fps）、破棄+54枚でした。旧RSSI無効版の同じ範囲では送信タイムアウト10回、接続11回、表示約250枚（約2.1fps）、破棄約43枚でした。新版の最初のタイムアウトは連番255（約42.5秒）、旧版は連番10（約1.7秒）でした。これは時間をずらした順次測定なので、無線状態の変動を含み、このコード変更だけでタイムアウト頻度や表示率が改善したと断定できません。

新版では送信タイムアウトのログから次のTCP接続受理まで、外部ログ時計の1秒分解能で約2秒と約7秒でした。タイムアウトを試みた動画連番から再接続後の最初の連番までの空白は3.3秒と9.5秒、旧版の最大は10.2秒です。長い動画時刻の空白は残ります。連番の空白は画面の厳密な停止時間ではありません。現行の診断には再接続時のWi-Fiリンク状態と再join有無がなく、7秒の内訳は確定できません。

省電力無効化 `cyw43_wifi_pm(..., CYW43_NONE_PM)` はWi-Fi参加前の起動時に1回呼び、PWS2の `pm_off=1` はその呼出しが0を返したことを示します。実効PMモードを後から読み戻した値ではありません。country codeはアプリに指定がなく、ローカルSDKの `cyw43_arch_init()` 既定 `CYW43_COUNTRY_WORLDWIDE` です。CYW43通信は内部ピンで動的に確保したPIOステートマシンと2本のDMAを使い、液晶は外部GP18/19のハードウェアSPI0で `spi_write_blocking` を使います。両者にSPI周辺回路やGPIOの直接競合はありません。CPU/メモリバスの同時負荷が損失に寄与するかはこの試験では確定できません。

### PM読み戻し診断

現ローカルCYW43ドライバ `c1075d4` の `cyw43_ll_wifi_pm()` は内部の設定ioctlの戻り値を検査せず、最後に0を返します。したがって上記の `pm_off=1` はPM無効化の証明ではありません。比較基準の稼働版を `/tmp/picow_pws2_tcp_only_reconnect.uf2` に保全した上で、Wi-Fi接続完了後に一度だけ公開 `cyw43_ioctl()` から `WLC_GET_PM` を読み、要求値 `CYW43_NONE_PM=0x10`（mode 0）と読戻しmode、読取りエラーをPi側ログへ載せる診断を追加しました。周期的な読み戻しはありません。PWS2の未使用だった11バイト目を使うため、状態パケットは60バイトのままです。`pm_readback=mode=0` は無効モードの読戻し、`mode=1/2` は省電力モードの読戻し、`error=N` はioctlエラー、`pending` は未取得を表します。PM設定の追加呼出しはしていません。

### 受信専用A/B版

表示版のCソースを `/tmp/picow_pm_readback_display.c`、表示版UF2を `/tmp/picow_pm_readback_once.uf2` に保全しました。受信専用版 `/tmp/picow_receive_only.uf2` は、動画ループ内の `lcd_show()` と表示時間計測だけをコンパイルから外します。LCD初期化と起動時3秒のテストパターンは従来どおりですが、動画フレームのLCD書込みはしません。受信フォーマット、2画面バッファへの格納と完成時のカウンタ更新、表示待ちスロットの解放、TCP処理、Wi-Fi維持、RSSI無効、PM設定と初回読み戻し、色補正には変更がありません。PWS2の既存フラグに `render=off` を表す1ビットを加えるだけで状態パケットは60バイトのままです。`displayed` は増えず、Piログは `display_rate=disabled` と表示します。

受信専用版は14件のソフトテストとSPI0版UF2のクリーンビルドに成功し、警告はありません。同じFlash ID `0xE661640843239D21` のPicoへ転送し、Flash Verify 100%・起動を確認しました。色調査用の設定は変えていません。同じ588枚・6fps・2秒送信期限の動画連番0〜720（約120秒）の比較は以下のとおりです。状態報告は約1秒刻みで、動画連番による区切りのためfpsは概算です。

| 項目 | 表示版 | 受信専用版 |
| --- | ---: | ---: |
| 受信完了枚数 (`received + dropped`) | 約656枚 / 5.47fps | 約570枚 / 4.75fps |
| 実描画枚数 | 約603枚 / 5.03fps | 0枚（描画無効） |

受信専用版ではPi側 `ss -tin` を0.25秒間隔で採取し、最初の約120秒の4接続について `bytes_retrans` の接続別観測最大値を合計すると**少なくとも1,096,380バイト**、同じサンプルでのACK済みバイトは約14,907,016バイトでした。RTO観測最大は3,456ms、指数バックオフ最大4、送信窓ゼロのサンプルはありません。再接続直前の値を採り損ね得るため再送数は下限です。表示版では同じ120秒の連続 `ss` 採取がないため、再送総量の定量比較はできません。別時点の表示版 `ss` 単発値は `bytes_retrans=80,400` / `bytes_sent=1,591,744` バイトで、再送の存在だけを示します。双方で送信停止と再送が観測され、LCD書込みを外しても通信停滞は残りました。順次測定中の無線状態の変動が大きいため、LCD負荷の小さな影響まで否定する結果ではありません。受信専用実機ログは `/tmp/picow_receive_only_live.log`、PiのTCPサンプルは `/tmp/picow_receive_only_tcp.tsv` です。

## RAW/JPEG 同一ファーム比較（実機試験済み）

PWF2比較ファームは後述のとおり同じPico Wへ転送済みです。現在の配信プロセスもPWF2を使います。既存の16150番や他サービスは対象外です。

新ファームは1回の書込みで次の5モードを使えます。Pi側の `--mode` を変えて配信プロセスを再起動すると、PicoがTCP再接続して新モードを受け取ります。PicoのUSBシリアル、1200baudリセット、ROSは使いません。RGB565の経路も保持しており、JPEGは採用決定ではなく帯域対CPUの比較用です。

| `--mode` | 受信 | JPEG展開 | 動画描画 | 比較対象 |
| --- | --- | --- | --- | --- |
| `raw-rx` | 25,600B RGB565 | なし | なし | RAW転送のみ |
| `raw-display` | 25,600B RGB565 | なし | あり | 現行表示に相当 |
| `jpeg-rx` | 最大8,192B JPEG | なし | なし | 圧縮転送のみ |
| `jpeg-decode` | 最大8,192B JPEG | あり | なし | 展開CPU負荷 |
| `jpeg-display` | 最大8,192B JPEG | あり | あり | 圧縮動画全体 |

`PWF2` は20バイトの固定ヘッダーで、`magic(4) / sequence(u32) / width(u16) / height(u16) / payload_length(u32) / mode(u32)` をすべてbig endianで送ります。幅・高さは160×80固定です。モードは各TCP接続の間固定し、変更は再接続時に受け入れます。RAWは25,600B固定、JPEGは4〜8,192B。過大JPEGはPiの準備段階でファイル名とサイズを示して拒否し、Picoでも過大ヘッダーを拒否します。画像を黙って切りません。JPEG展開前にSOI/EOI、寸法を調べ、不正JPEGは `decode_failed` に数えて描画しません。JPEG受信のみのモードは意図的に画素内容を解釈しません。

Piは元の588枚を読み取って品質90のJPEGへ再圧縮します。現画像と色補正を適用した場合、588枚すべてが8KiB以下で、最小1,798B、平均4,868B、最大6,454B、合計2,862,508Bでした。RAWの合計15,052,800Bに対して約5.26分の1です。色補正はRAWでは従来のRGB565変換後、JPEGでは圧縮前のRGB画素に適用します。この違いとJPEGの再圧縮により画素値は完全一致しません。

比較の開始例（Picoへの新UF2転送後、既存の本プロジェクト配信を停止してから1モードずつ）:

```sh
cd /home/tane/dev/PicoW/PicoW_Youtube_Player
python3 -m server --host 0.0.0.0 --port 16151 --frames /home/tane/Videos/voltesV_6frame --fps 6 --mode raw-rx --compensate-colors --trace-motion
# Ctrl+Cで止めてから、--mode を raw-display, jpeg-rx, jpeg-decode, jpeg-display へ変更
```

`--fps` は6以外も指定でき、後の高負荷試験で同じフレーム群を繰り返せます。今回の一次比較は同じ6fps・同じ動画・同じ2秒送信期限で行います。送信予定fpsと、Picoの受信完了fps、JPEG展開時間、実描画fpsは別の値です。安定6fpsやそれ以上の描画性能は、このホスト試験とビルドからは結論できません。

新しい逆方向状態 `PWS3` は80バイトで、従来のPWS2 60バイトに `mode`, `decoded`, `decode_failed`, `last_decode_us`, `max_decode_us` を各u32で追加しました。従来の `received` はスロットに受け入れた完全フレーム、`dropped` はスロット満杯で破棄した完全フレーム、両者の和が受信完了枚数です。`displayed` はLCDに書き終えた枚数で、JPEG受信・展開のみでは0のままです。`decoded` はJPEG展開成功枚数、`decode_failed` は展開エラー枚数。SPI時間とJPEG展開時間を個別に記録し、モードが切り替わると時間の最大値をリセットします。Pi側はPWS1/PWS2/PWS3を読み取れます。

JPEG展開器はローカルLovyanGFXにあるTJpgDecのC/H 2ファイルだけを `pico/third_party/tjpgd/` へコピーし、ライセンスコメントを保持しました。出典と条件は `THIRD_PARTY_NOTICES.md` を参照してください。ホストでデコーダの全588枚展開、不正/切断JPEG、過大JPEG、159×80の寸法違いを検査しました。Pico向けクリーンビルドのBSSは166,068B、`__end__=0x20028d9c` から `__StackLimit=0x20040000` まで94,820B残ります。別に8KiBのスタック領域が予約されています。この静的見積りは実行時ヒープ使用量の証明ではありません。転送に使用したUF2は `/tmp/picow_raw_jpeg_multimode_unflashed.uf2`（634,880B、SHA256 `9432eda69a5f5dc156e805304be1d91d3c49817bc4dcf56d0edf7d209547cec1`）です。ソフト試験17件が成功しました。ホスト上の展開時間はPicoの実測値ではありません。

この通信比較時点では旧LovyanGFXのST7735S初期化にgamma設定があり、当時のドライバにはありませんでした（後述のB版で追加・採用済み）。ただし現パネルの初期gamma値を確実に読み戻して復元する方法は確認できていないため、今回の同一ファームにはgamma切替を入れていません。通信比較では現行の色補正・`LCD_INVERT=1`・`LCD_MADCTL=0x60`・Yオフセット24を維持します。色調の比較は別の条件を混ぜずに行います。
